## 2 · Data Engine：五个资产，五种脏法

进 **Data Engine**。下面每一节建一个资产，流程都是四步：
**1·Sources → 2·Review → 3·Transform → 4·Publish**。

通用动作：
- 左上 **+** 新建资产 → 填名字
- **1·Sources** 里上传该组的原始文件（从 `test-data/dataeng-drill/` 里拖）
- **3·Transform** 里加步骤、配参数、看右边实时预览
- 预览对了再 **4·Publish**（Publish 会真跑 `dbt build` + 质量测试）

> 每加一个步骤，右边的预览会立刻重算。**先让预览对，再 Publish**——
> Publish 是跑 dbt 的，慢得多。

### 2.1 资产「01 销量」— union + 两次 enum_map

**建资产**，名字 `01 销量`，在 1·Sources 上传 `01_销量/` 下的 **4 个文件**。

上传后 Sources 里应该看到 4 个源表：
`a1_sales_mt2023` · `a2_sales_mt2024_2025` · `a3_sales_tt` · `a4_sales_ec`
（各 60 / 110 / 170 / 34 行）

到 **3·Transform**，依次加四个步骤：

**步骤 1 — Union**
- 类型 `union`，输入勾选上面 4 个源表
- 预览应为 **374 行**

**步骤 2 — Enum map（统一渠道）**
- 类型 `enum_map`，输入 = 步骤 1
- 字段选 `渠道`
- 点 **AI 建议 / 聚类**，它会把近似写法聚成组；逐组确认成：

  | 原始写法 | 统一为 |
  |---|---|
  | `现代渠道` `MT` `Modern Trade` `MT `(带尾空格) | `MT` |
  | `传统渠道` `TT` `Traditional Trade` | `TT` |
  | `电商` `EC` `E-Commerce` | `EC` |

- ⚠️ AI 给的建议里，**置信度低的会是 `proposed` 状态，不确认就不进数据**。
  只要还有 proposed 没处理，编译会直接报错告诉你还差几条——这是对的行为
- 确认完，预览里 `渠道` 列应该只剩 3 个值

**步骤 3 — Enum map（统一指标名）**
- 类型 `enum_map`，输入 = 步骤 2，字段选 `指标名称`
- `谈判点出货箱数` / `Compass完成箱数` / `Volume` 三个全部映射到 **`本品销量箱数`**

**步骤 4 — Field map（落到目标表）**
- 类型 `field_map`，输入 = 步骤 3，设为输出步骤

  | 目标列 | 来源 |
  |---|---|
  | `brand` | `品牌` |
  | `province_group` | `省份组别` |
  | `channel_type` | `渠道` |
  | `year` | `年` |
  | `month` | `年月` |
  | `metric` | `指标名称` |
  | `value` | `数值` |
  | `l1` `l2` `l3` | 常量 `'KPI'` |
  | `l4` | 常量 `'本品销量'` |
  | `metric_type` | 常量 `'Y'` |

#### ✅ 检查点 2.1
预览 **374 行**，`channel_type` 只有 MT/TT/EC，`metric` 只有 `本品销量箱数`。
去 **4·Publish** 发布，dbt build 应该通过。

### 2.2 资产「02 品牌媒体」— 一个 field_map 收拾三种毛病

**建资产** `02 品牌媒体`，上传 `02_品牌媒体/B_media_品牌媒体投放明细.xlsx`。
源表 `b_media`，240 行。

这份文件三个毛病：列名是英文缩写、金额是带千分位的**文本**、**完全没有渠道列**。

**唯一步骤 — Field map**（同时也是输出步骤）

| 目标列 | 配置 |
|---|---|
| `brand` | 表达式 `'MIZONE'` |
| `province_group` | 来源 `region` |
| `channel_type` | 表达式 `''`（**留空**） |
| `year` | 来源 `yr`，cast `integer` |
| `month` | 来源 `mnth`，cast `integer` |
| `l1` | 表达式 `'消费者需求驱动'` |
| `l2` | 表达式 `'品牌广告'` |
| `l3` | 来源 `factor_l3` |
| `l4` | 来源 `media_type` |
| `metric_type` | 表达式 `case when metric_nm = '花费' then 'spending' else 'X' end` |
| `metric` | 来源 `metric_nm` |
| `value` | 表达式 `cast(replace(spend_txt, ',', '') as double)` |

> **`channel_type` 为什么必须留空？** 这是全国投放的品牌媒体，一次买断打给所有渠道。
> 留空是引擎识别"全国因子"的信号，它会被共享进**每一个** (渠道×品牌) 模型对象。
> 要是随手填个 `MT`，OTT/OOH 这些媒体就只进 MT 模型，TT 和 EC 的模型会凭空少掉一半媒体。

#### ✅ 检查点 2.2
预览 **240 行**；`value` 是数字不是文本（列头统计能看到 min/max/均值）；
`channel_type` 整列为空。发布。

### 2.3 资产「03 电商」— join + aggregate

**建资产** `03 电商`，上传 `03_电商/C_ecom_电商投流与促销.xlsx`。

`c_ecom___detail`（204 行）和 `c_ecom___lookup`（4 行）。

- 类型 `join`，输入 = `c_ecom___detail`（左）+ `c_ecom___lookup`（右）

> 对照表里有个 `拼多多`，明细里根本没有。left join 之后行数应该**还是 204**，
> 没有凭空多出来的行——这就是在验证 join 不会造数据。

**步骤 2 — Aggregate**

- Group by：`年月` `渠道类型` `省份组别` `因子L1` `因子L2` `因子L3` `因子L4` `指标`
- 聚合：`金额` → `sum`，别名 `金额`

### 2.4 资产「04 线下促销周报」— filter + derive + aggregate

**建资产** `04 线下促销周报`，上传 `04_线下促销周报/D_weekly_线下促销周报.csv`。
源表 `d_weekly`，**4280 行**（周 × SKU 粒度）。

**步骤 2 — Derive**

- 新列名 `month`，表达式：

**步骤 3 — Aggregate**
- 类型 `aggregate`，输入 = 步骤 2
- Group by：`month` `channel_type` `province_group` `factor_l3` `factor_l4` `metric_name`
- 聚合：`value` → `sum`，别名 `value`

**步骤 4 — Field map**（输出步骤）

| 目标列 | 配置 |
|---|---|
| `brand` | 表达式 `'MIZONE'` |
| `province_group` | 来源 `province_group` |
| `channel_type` | 来源 `channel_type` |
| `year` | 表达式 `cast("month" / 100 as integer)` |
| `month` | 来源 `month`，cast `integer` |
| `l1` | 表达式 `'渠道成交驱动'` |
| `l2` | 表达式 `'渠道'` |
| `l3` `l4` | 来源 `factor_l3` `factor_l4` |
| `metric_type` | 表达式 `'spending'` |
| `metric` | 来源 `metric_name` |
| `value` | 来源 `value`，cast `double` |

## 3 · 孤儿指标：数据给了、但因子树没要

去 **Data Engine → Indicators**。除了正常挂到因子树上的指标，会另有一组
**孤儿指标（orphans）**——数据供上来了，但因子树里没有对应的行。

实测 **3–4 条**：

| 孤儿 | 为什么 |
|---|---|
| `电商站内投流 > 站内投流 > 花费` | 模板把它放在 `电商平台媒体及促销` 底下当 L4，路径对不上 |
| `促销优惠 > 促销优惠 > 花费`（来自 03 电商） | 模板把促销拆成 `组合优惠` / `单品折扣`，没有平的 `促销优惠` |
| `促销优惠 > 促销优惠 > 花费`（来自 05 门店） | 同一个指标故意拆在两个文件里，所以有两条 coverage 记录 |
| `促销优惠 > 促销优惠 > PPI` | 同上（若 AI 从访谈里补出了一条 `促销优惠` 的因子行，PPI 可能被它接住而不再是孤儿） |

> **一个因子行只会被一个指标认领。** 粗粒度匹配（只按路径、或只按 L3）不知道自己在
> 匹配哪个指标，如果不加限制，`促销优惠` 下的「花费」和「PPI」会同时挂到同一行上——
> 那一行显示"已供数"，两个指标也都显示"已归位"，实际上全是假的。
> 现在同一行被第二个**不同**指标碰到时不再重复认领，认不上的就是孤儿，交给 2.1 处理。
> （同名指标由多个数据源共同供数仍然允许，那是设计内的场景。）

> **`本品销量箱数` 不在这里，这是对的。** 行业因子树描述的是"什么解释了销量"，
> 所以任何模板都不会声明销量本身。它按**响应变量（Y）**识别，不进孤儿列表，
> 也不允许被采纳进因子树——那等于让被解释变量变成自己的驱动因子。
> 它在 2.6 因子树收口里以 `role=response` 出现。

> 数量可能有 ±1 的浮动。因子树里有一批行是 AI 从真实访谈里抽出来的，每次 S1
> 措辞不完全一样，偶尔会正好接住其中一条。前四条到底算不算孤儿，取决于你确认的
> 那棵树——这本身就是要观察的东西。

对前面几条（**不含 Y**）各做一次处理，两种都试一下：
- **采纳（Adopt）**：把它加进因子树并挂上供给，来源标记为 `data_upload`
- **驳回（Dismiss）**：确认这个指标不进模型

> 采纳会**真的改写因子树**。想反复测的话记得 2.6 检查完再重来。

### ✅ 检查点 3
采纳的那些，会立刻出现在因子树里并显示已供数；驳回的从指标目录里消失。
两种操作都**不需要**重新发布资产。

## 4 · Data Intake & Validation（2.1 → 2.6）

回 **Workflow Canvas**。**把 Autopilot 关掉**——这一段每个门都要你自己判断，
autopilot 会替你点掉，那就白测了。

### 4.1 · 2.1 Data Processing（因子映射）

打开 2.1。左边是因子树的每一行，右边是 AI 给它提的候选指标。每一行三选一：
**接受 / 换一个 / 忽略**。

- 有数据供的行，AI 提的候选一般是对的，接受即可
- 没有任何数据的行（尤其是访谈抽出来的那批英文路径），选**忽略**并写上理由
- 全部处理完，2.1 的 gate 才会放行

> **重点看这里**：AI 提的候选**并不总是对的**。因子树里同一条 L1–L4 路径下往往有
> 好几行（分别声明不同的 indicator），而自动匹配只认路径、不认 indicator。
> 所以你会看到「`品牌传播 > OTT` 这一行声明的是曝光量，却被挂上了花费」这类情况。
> 遇到就用**换一个**改掉——这正是这个界面存在的意义。

#### ✅ 检查点 4.1
因子映射全部 resolved（mapped 或 ignored），2.1 通过，2.1d 出现映射覆盖度总结。

### 4.2 · 2.2 数据质量打分

跑 2.2，产出 `a-quality-scorecard`：10 项子检查 + AI 的四维度打分
（一致性 / 准确性 / 完整性 / 颗粒度）。

在 **2.2d** 逐行看 AI 的判定。**注意**：这份数据里 EC 渠道的部分线下执行指标
本来就很稀疏（真实数据就这样），完整性被打低是**正确**的，不是 bug。

> 打分是按**指标**记的，一个指标只判一次，所有模型对象继承同一个结论。

#### ✅ 检查点 4.2
至少有几个指标因为完整性/颗粒度被标出来。你在这里 **Drop** 掉的指标，
后面 2.4、2.5 都不会再出现——这就是"逐层继承"。**记下你 drop 了哪个**，
到 4.5 去核对。

> **每一行都必须给出二态判定才能过门。** AI 给的 `flag`（2.2）/ `review`（2.4）
> 只是"待你看一眼"的初始值，不是判定。只要还有一行停在这个状态，
> 点关门会被拒绝并列出还差哪几个指标。
> 这是刻意的：以前 `review` 不被下游读取，等于**静默放行**——曾经有 6 个指标
> 就这么进了模型，其中一个把整个拟合搞坏了。

### 4.3 · 2.3 业务验证 + 异常解释

2.3 出的是按因子的图表页（Y 用面积图、花费用折线、其他用柱状）。
2.3a 会给每个检出的异常配一条 AI 假设 + 处理建议：

- `event` — 当作事件，在该窗口加一个哑变量控制
- `cap` — 缩尾处理
- `raw` — 只记一句说明，不动数据

至少**接受一条** `event` 或 `cap`，好验证它是真的会影响后面的建模
（接受的处理会真的进模型，pending/rejected 的什么都不做）。

然后在 2.3s 做客户签署。

### 4.4 · 2.4 统计初筛

CV / Pearson / VIF 三项检验 + AI 逐行判定。在 2.4d 复核。

> 相关性是在**面板**上算的：每个 (模型对象, 月份) 一行，同比差分在每个对象**内部**做。
> 区域和 L5–L8 在单元格内部先按该指标的聚合方式卷起来。

#### ✅ 检查点 4.4
4.2 里被 drop 的指标，在 2.4 的表里**不应该出现**。

### 4.5 · 2.5 OLS 分渠道×产品建模

这一步会按 (渠道类型 × 品牌) 逐个建模。这份数据应该得到 **3 个模型对象**：
`MT · MIZONE`、`TT · MIZONE`、`EC · MIZONE`。

`16个竞品` 只有投入、没有销量，**不会**成为模型对象——它的行会作为市场背景
共享进每一个模型（竞品投放影响所有人，不属于任何人）。

2.5 只负责拟合，不做判定。判定在下一步 **2.5d** 做。

#### ✅ 检查点 4.5 （最关键的一个）

| 要确认的 | 期望（括号内是我实测到的值，你的会有出入） |
|---|---|
| 模型对象数 | 3 个：`MT · MIZONE` `TT · MIZONE` `EC · MIZONE` |
| **每个对象的全国媒体** | 每个都应拿到 **5 个**无渠道的全国指标（OTT/OOH/热剧/Digital Display/社媒） |
| 每个对象的候选驱动 | 16–18 个（实测 MT 18 · TT 16 · EC 18） |
| 实际入模变量 | 每个 5–7 个（实测 7 / 5 / 7），`n=34` 个月，剩余自由度 25–27 |
| 拟合优度 | R² 大致 0.84–0.89（实测 0.885 / 0.843 / 0.860） |
| 被 drop 的指标 | 4.2 和 4.4 里 drop 的，在三个模型的变量表里**一个都不该出现** |
| 未勾选的变量 | 若有，理由应该是**自由度限制**（34 个月放不下那么多变量），而不是"被判差" |
| ROI / Contribution | 按模型对象分别看，不是一个混在一起的视图 |

> 红旗（red flags）出现是**正常的**，别当成 bug：这是真实数据。MAPE 超出 5–15%
> 基准、DW 偏低这些，是真实存在的数据问题，模型能标出来正是它该做的事。

**怎么读 Contribution。** 每个因子树变量都**单独**算贡献，不会被并进 baseline
（换个项目因子树就变了，没有"合并"这回事）。恒等式是
`baseline + Σ所有因子贡献 = 100%`，你可以自己加一遍核对。

贡献值下面会标**参照基准**，因为"贡献了多少"必须先说清楚"和什么比"：

| 变量类型 | 参照 | 显示 |
|---|---|---|
| 花费类 | 零 | `vs zero`——不投放就没有增量，这是真增量 |
| 水平/比率类（价格、铺货率、温度） | 窗口内最低值 | `vs its lowest month (x)` |

价格 3.5 元、铺货率 600、温度 21℃ 这类变量永远不会归零，拿它们和零比等于把整个
存量水平算成"贡献"——那正是之前出现 `竞品ND −1907%`、`本品标价 +1415%` 的原因。
低于参照的那部分归入 baseline，所以恒等式仍然精确成立。

**可能会看到变量被引擎剔除。** 设计矩阵 VIF > 100 的变量会被剔出拟合并注明原因。
这不是"判它不好"，而是它在这批数据里**不可识别**——被其他变量解释到 R² > 0.99，
系数是浮点噪声。和自由度上限是同一类规则。中度共线（VIF > 10）仍然只是红旗，
留给你自己判断。

> 全国媒体这条特别值得看。34 个月、每个模型十几个驱动，一旦全国媒体没被共享进去，
> 每个模型会少掉一大半媒体变量——这是这份数据专门用来抓的问题。

### 4.5b · 2.5d 逐因子采纳判定（新）

打开 **OLS Regression Test → Factor tree · verdicts** 页签（Process 里的 2.5d 步骤
内嵌的是同一个面板）。每个已拟合的因子都带一条 AI 建议：

| 情况 | 建议 | 为什么 |
|---|---|---|
| ROI / Contribution 落在知识库区间内 | **Accept** | 算术通过 |
| 落在区间外 | **Reject** | 理由里会写具体是哪个数超了 |
| 无区间基准，但 AI 判定 implausible | **Reject** | 没有区间可证伪时，这是唯一的信号 |
| 区间内但 AI 存疑（questionable） | **Accept**（附提示） | 算术通过；把存疑变成拒绝等于删掉没人决定删的变量 |

只有 **Accept / Reject** 两态，没有中间状态——这是最后一层，留一个"待定"就等于
让变量在没人点头的情况下进模型。

#### ✅ 检查点 4.5b

1. 改一行的判定（比如把某个 Reject 改成 Accept），点 **Save & refit**。
2. 该行应显示 **overrides the recommendation (reject)**：AI 的建议还在算、还在显示，
   但你的判定说了算。
3. 再点一次 Save & refit（不做任何修改）——**判定和数量都不应该再变**。
   你手动改过的行永远不会被重新拟合冲掉。
4. 被 Reject 的变量会**离开模型**，剩下的系数是在没有它的情况下重新估的。
   这不是 bug，是诚实的结果：拒绝一个变量本来就会改变其他变量的系数。

> 为什么"再存一次不该变"值得专门测：拟合用的是当时那套判定，而判定表是**从这次
> 拟合结果推出来的**——所以一个新掉出区间的因子，是在包含它的那个模型已经渲染完
> 之后才被拒绝的。只跑一遍，交付物就会展示一个"它自己的判定要拒绝掉"的模型。
> 后端会自动多拟合一轮直到收敛。

然后在 d-2.5 决策门签署。

> ⚠️ **d-2.5 一旦签署，2.2 / 2.4 / 2.5 就锁死了。** 再去改上游判定会被拒绝（HTTP 409），
> 因为 2.6 是基于当时那套判定拟合出来的，改了就等于模型声称的筛选链和它自己
> 对不上。真要改，得先重开 d-2.5，再改、再重跑下游。

### 4.6 · 2.6 Master Data

2.6 产出 `a-master-data`：漏斗 + 维度 + 每个指标的完整判定链。宽表是按
产品 × 渠道 × 区域**实时查**的，可以切着看。

点 **Export .xlsx** 导出 2.32 交付物，应该拿到 **2 + N 个 sheet**（N = 模型对象数）：

| Sheet | 内容 |
|---|---|
| `模型颗粒度参考表` | 每条因子行的渠道 × 区域颗粒度；未采纳的两列留空 |
| `D.Data Station` | 采纳指标的长表原始行，**不截断**，**含 Y** |
| 每个模型对象一张 | 宽表：一行一期，一列一个指标，Y 在第一列 |

#### ✅ 检查点 4.6a — 三个口径必须一致

这是这次专门修的地方，值得自己核一遍：

1. `模型颗粒度参考表`里 adopted 的行数，应当等于因子树收口里 `adopted + partial`
   的行数（实测两边都是 **6**）。
2. `D.Data Station` 里必须**有 Y**（`本品销量箱数`）。之前这里会把 Y 整个滤掉——
   Y 不是驱动、不在台账里——导出的"model input"没有因变量。
3. 每个模型对象的 sheet，列出来的驱动应当和 2.5 里那个模型**实际入模的变量完全一致**。
   特别看**全国指标**（温度、竞品ND 这种没有渠道的）：某个渠道拒了它，
   不应该让保留它的那个渠道也丢掉。

#### ✅ 检查点 4.6
因子树收口视图里，每一条 active 因子行都应该有一个判定：

| 判定 | 含义 |
|---|---|
| `adopted` | 进了模型 |
| `partial` | 有的模型进了、有的没进 |
| `rejected` | 被某一层判掉了（会标出**最早**判掉它的那一层） |
| `notModeled` | 有数据但没进模型 |
| `notSupplied` | **压根没数据**（访谈抽出来的那批英文路径应该都在这里） |

`notSupplied` 和 `rejected` 是两回事：前者没人给数据，后者是有人判过。

**这一步最值得看的是「继承」有没有真的生效。** 我实测的收口结果：224 条 active 因子行里
6 条 `adopted`，而**在 mapping 之后被判掉的只有 1 条**——
`渠道执行 > 销售业代对于产品陈列的执行 - 位置好 [销售业代视平线达成率]`，
标注为 `at statistical`。它正是 2.4 里因为相关性和共线性双双不过被判 0 分的那个指标：
2.5 没有重新给它打分、没有再把它作为候选提出来，2.6 直接引用了 2.4 的结论。
这就是"一层拒绝、层层继承"该有的样子。

> 其余 200 多条被标为 `rejected / mapping` 的，是 AI 从真实访谈里抽出来的因子行
> （`Sub-channel > EC B2B`、`CityClassification` 这类）。它们确实没有任何数据，
> 你在 2.1 把它们忽略掉，所以算"有人判过"。这是对的。

最后在 2.6d 锁定 Master Data。

## 附录 · 这套演练第一次跑就抓到的两个问题（均已修复）

留在这里当参考：这是"跑一遍真数据"和"看代码觉得没问题"的区别。

### A · 因子行的身份是「路径 + 指标」，不只是路径

因子树里同一条 L1–L4 路径下经常有**好几行**，各自声明不同的 indicator
（`店内促销 > 旺点促销` 下面既有「花费」也有「执行门店数」）。
但 `claim_published_metrics` 用的是 `{路径: 行}` 的字典推导——后写的兄弟行覆盖先写的，
而且**完全不看 `indicator` 字段**。

结果：16 条自动绑定里 **8 条挂错了行**，而且每条正确的兄弟行都真实存在。
「温度」挂到了声明「降水量」的行，「竞品ND」挂到了「竞品WD」，
「已投放冰柜个数」挂到了「花费」。全部标记为 `boundBy="auto"`，
后面**没有任何一层会重新审视**，一路错到 2.6 的因子树收口——
一边报告某行已采纳，一边报告它的兄弟行「无数据供给」，两个都是假的。

更糟的是两个解析器不一致而粗的那个赢了：`indicators.resolve_coverage` 本来就有
按 `(l3, indicator)` 的精确兜底，但因为发布时已经**写入**了 `tree_row_id`，
读取侧的第一优先级（"已显式绑定"）直接采信了错误值，精确匹配永远不会执行。

**修法**：两边都改成由细到粗匹配 `(路径,指标) → 路径 → (l3,指标) → l3`。
保留纯路径那一档很重要——没有任何兄弟行声明的指标仍应挂在它已知的因子上，
而不是变成孤儿。回归测试：`app/dataeng/_test_claim.py`。

### B · Autopilot 会在数据发布之前就把整棵因子树判成「无数据」

Autopilot 一跑完 S1 就到 2.1，而这时 Data Engine 还一次都没用过。
`auto_resolve_factor_map` 于是给**全部 240 行**写上"没有任何已发布指标匹配此因子"。
但忽略记录会持久化，而且**忽略优先于已映射**——之后再怎么发布数据也无法解除。

后果是整个 S2 被掏空：因子映射永远 `mapped=0`，指标台账在 mapping 这一层就砍掉 223 个，
2.5 建模时 MT 只剩 2 个驱动、TT 一个都没有、EC 剩 2 个——而数据里实际有 16–18 个。

而这正是本指南推荐的操作顺序（S1 开 autopilot → 再做数据），所以这个 bug
会稳定地毁掉每一次演练。

**修法**：项目一条 coverage 都没有时，`auto_resolve_factor_map` 直接返回，不写任何忽略。
"这个因子没有数据"是对数据的判断；没有数据可判的时候，它什么也不是。
Autopilot 应该像人一样卡在 2.1。回归测试：`app/dataeng/_test_mapping_coverage.py`。
